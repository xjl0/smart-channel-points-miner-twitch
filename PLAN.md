# Smart Twitch Points Miner — план работ

> Статус: **УТВЕРЖДЁН, этапы 0–10 выполнены.** Каждый этап — отдельный коммит.
> Не проверено на живом аккаунте: этапы 2–5 и 7 (вход, minute-watched → 204, чат, суточный прогон) — см. раздел 10.

## 1. Цель

За каждую трансляцию отслеживаемых каналов получать **стрик просмотра**, не вызывая подозрений у Twitch.
Баллы за минуты и сундуки — побочный эффект.

## 2. Что не так в референсе (и что берём)

| Проблема в референсе | Как делаем у себя |
|---|---|
| `pickStreamersToWatch` — ~450 строк, логика «кого смотреть» размазана по `miner.go` (2100 строк) вместе с кэшами и таймерами | Планировщик — **чистая функция** `Decide(state, now) → []slot` (≤2), без I/O, табличные тесты |
| Состояние в памяти + JSON warm-start кэш + cookies-файлы | Всё в **SQLite**. Рестарт = продолжаем с того же места |
| `RewardList` дёргается на **каждый** minute-watched | RewardList — при старте стрик-попытки и раз в ~3 мин во время неё; основной сигнал — PubSub `WATCH_STREAK` |
| Предсказания, рейды, дропы, моменты, goals, Discord, апдейтер, анонимайзер | **Выкидываем** |
| Самописный логгер | `log/slog`; каждое действие → лог + `events` в БД + live-канал админки |

Берём (переписывая чисто): device-code логин, GQL persisted queries, spade URL + `minute-watched`,
PubSub (`video-playback-by-id`, `community-points-user-v1`), клик сундука (как в референсе), IRC-чат.

## 3. Правила поведения

### 3.1 Определение онлайна
1. **Старт приложения**: по каждому включённому каналу — разовая проверка онлайна (GQL StreamInfo),
   запросы **разнесены** во времени (1–3 с между каналами), а не пачкой.
2. **Дальше**: PubSub `stream-up` / `stream-down` по каждому каналу.
3. **Страховка**: редкий опрос (раз в 10–15 мин с джиттером) на случай потерянных событий PubSub.

### 3.2 Слоты (жёстко не более 2)
Каждый слот имеет причину: `streak` (ловим стрик) или `fill` (просто смотрим).

1. **Очередь стриков** — онлайн-каналы, у которых стрик за текущую трансляцию не получен,
   в порядке выхода в онлайн (FIFO).
2. **Текущую стрик-попытку добиваем** — новый стример в онлайне её не вытесняет, а встаёт в очередь.
3. **15 минут просмотра без стрика → считаем стрик полученным** (скорее всего, он был взят раньше, например
   с другого устройства). Считается время просмотра этой трансляции (переживает рестарт), канал отпускается,
   берём следующего из очереди. *(Изменено по ходу работ; было «таймаут 10 мин, до 2 попыток».)*
4. Стрик получен → досматриваем 1–5 мин (рандом), освобождаем слот.
5. `streak` всегда важнее `fill`: если в очереди есть стрик, `fill`-слот освобождается под него.
6. **Нет стриков в очереди** → `fill`: онлайн-канал, который **меньше всех смотрели за его текущую трансляцию**
   (счётчик живёт от начала стрима до конца, без привязки к суткам; новая трансляция — счётчик с нуля).
   Канал в `fill` держим минимум ~30 мин (±рандом), чтобы не прыгать между каналами каждую минуту.
7. Никого онлайн — не смотрим никого.

### 3.3 Присутствие и «не наглость»
- Пока канал в слоте — `minute-watched` раз в минуту (с джиттером) + **IRC `JOIN`** под своим аккаунтом
  (видны в чате). Вышли из слота — `PART`. **В чат ничего не пишем.**
- Сундук: кликаем, как в референсе, с человеческой задержкой.
- Один стабильный Client-ID / User-Agent / device-id на аккаунт; глобальный rate-limiter GQL; backoff на ошибки.

## 4. Архитектура

**Один бинарь, один процесс** с чёткими модулями. `api` знает о `engine` только через интерфейс и шину событий.

```
cmd/miner/main.go            — сборка зависимостей, запуск, graceful shutdown
internal/
  config/                    — env (порт, путь к БД, уровень логов)
  store/                     — SQLite: миграции + запросы (sqlc). Единственное место с SQL
  twitch/                    — один пакет с общим HTTP-клиентом/идентичностью (иначе подпакеты тянули бы друг друга):
    client.go                — заголовки TV-клиента, rate-limit GQL, build id
    auth.go                  — device-code логин, validate токена
    channels.go              — GQL: ChannelID, StreamInfo, WatchStreak, ChannelPoints, ClaimBonus
    spade.go                 — spade URL (глобальный, кэш 6 ч) + minute-watched
    pubsub/                  — WebSocket, подписки → типизированные события
    chat/                    — IRC поверх WebSocket (как веб-плеер), Join/Part, PING/PONG, реконнект
  jitter/                    — случайные задержки для всего, что идёт по таймеру
  engine/
    scheduler.go             — чистая Decide (сердце логики)
    slot.go                  — один слот: цикл minute-watched + чат
    engine.go                — события → состояние → Decide → старт/стоп слотов
  live/                      — шина событий: seq-номера, кольцевой буфер, снапшот (см. 6.2)
  api/                       — Connect хендлеры, SSE, Basic-авторизация (админку раздаёт Caddy, см. §11)
proto/miner/v1/*.proto
web/                          — Vite + React + TS + shadcn/ui + connect-es + TanStack Query
Dockerfile
```

```
PubSub / старт-проверка / страховочный опрос ─┐
Команды админки ──────────────────────────────┼─► engine ─► Decide ─► слоты (≤2) ─► spade + IRC
                                              │      │
                                              │      └─► live (seq++) ─► slog / SQLite / стрим в админку
```

## 5. Схема БД (SQLite, `modernc.org/sqlite`, без CGO)

- `account` — login, user_id, token, client_id, device_id
- `channels` — id, login, display_name, enabled, added_at
- `broadcasts` — id, channel_id, started_at, ended_at, streak_claimed_at, streak_value, streak_attempts
- `watch_sessions` — id, channel_id, broadcast_id, reason (`streak`|`fill`), started_at, ended_at, seconds
- `events` — seq (PK), ts, type, channel_id, payload BLOB (protobuf) — та же лента, что уходит в админку

«Меньше всего смотрели» = `SUM(seconds)` из `watch_sessions` по **текущему** `broadcast_id` канала.

## 6. API

### 6.1 Unary RPC (Connect, `MinerService`)
`ListChannels`, `AddChannel(login)`, `RemoveChannel`, `SetChannelEnabled`, `ListEvents(before_seq)`,
`StartLogin`, `GetLoginState`.

### 6.2 Live-канал: бинарный protobuf-стрим со снапшотом и дельтами (предложение)

**Транспорт**: Connect **server-streaming** RPC `Subscribe(SubscribeRequest) returns (stream LiveMessage)`
в бинарном формате (`application/connect+proto`). Это обычный HTTP-ответ, который не закрывается;
внутри — кадры `[1 байт флаги][4 байта длина][protobuf]`. В браузере читается через `fetch` + `ReadableStream`
(connect-es с `useBinaryFormat: true`). По сути — семантика SSE, но бинарно и типизировано тем же proto.

**Протокол «снапшот + дельты + докачка»** (как в репликации БД / игровом неткоде):
1. Клиент подключается с `since_seq` (0 при первом заходе).
2. Если `since_seq` есть в кольцевом буфере сервера (последние ~1000 событий) — сервер досылает пропущенные
   дельты. Иначе — сначала полный `Snapshot`, потом дельты.
3. Каждое сообщение несёт монотонный `seq`. Клиент применяет дельты к локальному состоянию (reducer),
   пропуск seq → переподключение с последним seq.
4. `Heartbeat` каждые 15 с — UI видит «соединение живо», прокси не рвут стрим.

**Что передаём** (`LiveMessage { uint64 seq; Timestamp ts; oneof body }`):

| Сообщение | Когда | Что в нём |
|---|---|---|
| `Snapshot` | при подключении без докачки | аккаунт, все каналы с состоянием, оба слота, очередь стриков |
| `ChannelUpdated` | онлайн/оффлайн, новая трансляция, стрик получен, вкл/выкл | полное состояние одного канала |
| `SlotChanged` | слот занят/освобождён | номер слота, канал, причина (`streak`/`fill`), started_at, дедлайн попытки |
| `QueueChanged` | изменилась очередь стриков | упорядоченный список channel_id |
| `WatchTick` | каждая успешная minute-watched | channel_id, секунд за текущую трансляцию |
| `PointsGained` | PubSub points-earned | channel_id, +баллы, причина, баланс |
| `StreakResult` | стрик получен / таймаут попытки | channel_id, успех, значение стрика, номер попытки |
| `LogEntry` | warn/error из slog | уровень, сообщение, атрибуты |
| `Heartbeat` | каждые 15 с | — |

Принцип: **состояние меняют только `Snapshot` / `ChannelUpdated` / `SlotChanged` / `QueueChanged`** (полное
состояние сущности, а не «+1»), поэтому клиент не разъезжается с сервером; остальные — лента событий.

## 7. Админка (shadcn/ui)

- **Дашборд**: 2 карточки слотов (канал, причина, сколько смотрим, таймер до таймаута попытки), очередь стриков, live-лента.
- **Каналы**: таблица (онлайн, стрик за трансляцию, длина стрика, время за трансляцию), добавить/удалить/выключить.
- **Аккаунт**: статус, device-code вход.
- **События**: история с фильтрами (подгрузка `ListEvents`).
- Индикатор соединения live-канала (по heartbeat).
- Без авторизации на время разработки.

## 9. Решения (из ответов)

1. Один процесс. 2. Live — бинарный protobuf (6.2). 3. Старт-проверка онлайна + PubSub + страховочный опрос.
4. Один аккаунт. 5. Сундуки кликаем. 6. Добиваем текущий стрик, очередь FIFO, таймаут 10 мин.
7. «Меньше смотрели» — за текущую трансляцию. 8. Логин из админки. 9. Без пароля пока. 10. Docker. 11. Стек ок.

## 10. Отклонения от плана и что осталось

Отклонения (по ходу работ):
- `twitch/auth|gql|spade` — файлы одного пакета `twitch`, а не подпакеты (общий клиент и идентичность).
- Proto-контракт и шина `live` написаны в этапе 7 (движку нужен формат событий), API поверх них — этап 8.
- В БД нет таблицы `settings`: параметры политики — константы в `engine.DefaultPolicy()`.
- TanStack Query подключён позже: кэш истории событий (useInfiniteQuery) и команды админки (useMutation); остальное состояние — из live-потока.
- Runtime-образ на alpine вместо distroless (gcr.io доступен не из всех сетей) + healthcheck.
- Случайный разброс: досмотр после стрика 2–4 мин, удержание fill 20–40 мин (±1/3 от 3 и 30 мин).
- Каналы в БД хранят `points` и `streak_length` (нужны для таблицы каналов).

Осталось проверить вживую (нужен вход в аккаунт):
- device-code вход из админки, токен переживает рестарт;
- `minute-watched` → 204, аккаунт виден в чате канала;
- PubSub: stream-up/down, points-earned, `WATCH_STREAK`; клик сундука;
- суточный прогон: стрики ловятся, слотов ≤ 2, таймаут попытки 10 мин срабатывает.

## 11. Изменения после запуска (2026-11-22)

- Live-канал переведён с Connect server-streaming на **SSE** (`GET /live`): JSON-события `LiveMessage`,
  `id: <seq>` у дельт и снапшотов → браузерный `EventSource` сам докачивает через `Last-Event-ID`.
  Команды остались unary Connect RPC.
- Стрик: «15 минут просмотра без стрика → считаем полученным» (`MINER_STREAK_ASSUME_AFTER`).
- PubSub: одна тема на кадр LISTEN; без живого PubSub Twitch не засчитывает просмотр (см. docs/twitch-traffic.md).
- Трассировка сырого трафика: `MINER_TRACE_DIR` (в compose → `./trace`).
- Админку раздаёт отдельный контейнер **Caddy** (`web/Caddyfile`): статика, HTTP Basic авторизация,
  прокси `/miner.v1.*` и `/live` в Go. Go — только API, наружу не публикуется; встраивание UI в бинарник убрано.
